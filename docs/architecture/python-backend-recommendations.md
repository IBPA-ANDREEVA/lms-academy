# Python backend recommendations

These are prioritized engineering proposals for future implementation, not installed dependencies or resolved business policies. The owner-selected stack and two-runtime boundary are accepted in [ADR-0003](../decisions/0003-python-backend-architecture.md). Resolve each remaining selection within the affected capability preparation; do not block unrelated work behind a global platform redesign.

| Priority / decision point | Recommendation and reason | Acceptance evidence / unresolved selection |
| --- | --- | --- |
| P0 — Identity initialization: authentication | Prefer one browser origin with ingress forwarding to FastAPI and a revocable opaque HttpOnly/Secure cookie owned by Identity. Use a maintained compatible auth/password library; avoid a second Next.js session database and long-lived browser tokens. | Choose library/provider, session store, cookie policy and CSRF defense; test SSR forwarding, rotation/logout, block enforcement, forged requests and recovery. OQ-013/016/032 remain business dependencies. See the [session contract](frontend-backend-integration.md#authentication-and-session-boundary). |
| P0 — first API integration: generated client | Evaluate `@hey-api/openapi-ts` against actual FastAPI OpenAPI, with pinned generator and reproducible export. Keep generated transport types separate from UI view models. | Confirm nullable/optional/enum/error handling, server/browser transport and cancellation; choose artifact paths and CI drift/breaking-change checks. No generator is installed or mandated by this recommendation. |
| P0 — persistence initialization: connections/sessions | Start by evaluating synchronous SQLAlchemy 2 with psycopg 3 for simple transaction flow; keep blocking work out of async event loops. Choose async only for concrete concurrency needs and compatible adapters. Use a bounded process-level engine pool and one session per request/job unit of work. | Choose driver/sync model, total connection budget across replicas/workers, timeouts and Neon topology. Benchmark expected load/cold-start/reconnect behavior. Never share sessions between concurrent tasks. |
| P0 — first cross-module write: transactions | Let the initiating domain operation own commit/rollback; pass explicit transaction context through narrow local commands. Use constraints/version checks/locks for replay and races. Payment confirmation + order + enrollment, and refund + revocation, must commit together. | PostgreSQL tests prove rollback, uniqueness, concurrent duplicate callbacks and conflict outcomes. No HTTP calls between the seven Python modules; no raw table writes through another domain. |
| P0 — first durable effect: jobs/outbox | Prefer a PostgreSQL transactional outbox before adding a broker. Commit a minimal durable fact with the business state, then use separate Python workers with claim leases, retries/backoff, crash recovery and attention state. | Select executor/polling/queue library and recovery runbook; test crashes before/after commit, duplicate delivery, lease expiry and delayed reminders. At-least-once execution requires idempotent handlers. PD-003 retains one concurrent FFmpeg job, three automatic retries and manual recovery. |
| P1 — initialization/local development and release | Keep pnpm frontend and uv backend environments in this repository. Pin supported Python and package versions, recommend mypy with focused strictness, run pytest/Ruff/type checks in backend CI, and retain frontend checks. Use isolated local/test PostgreSQL or a verified isolated Neon branch. | Add manifests/lockfile, real run commands and CI only in the initialization task. No container/orchestration files or sample services are required by this architecture task. Never use production student data or credentials for tests. |
| P1 — deployment topology | Deploy Next.js and Python API independently, with separately supervised Python workers and the approved separate FFmpeg VPS/VM. Prefer API/database proximity and one ingress browser origin. Run Alembic once as a controlled release step with expand/contract compatibility. | Select hosts, regions, TLS/secrets, readiness/draining, worker resource limits and connection budgets. Test frontend/API version overlap, migration forward repair, API outage behavior and queue recovery. Neon is intended, not provisioned/launch-verified. |
| P1 — before production acceptance | Trace safe correlation IDs through HTTP/webhooks/jobs, monitor queue age and critical workflow outcomes, and rehearse restore/rollback with deletion safeguards. | OQ-078/079/080/081 and PD-007 legal retention/recovery requirements remain open where recorded. Do not infer RPO/RTO, legal periods or budget guarantees. |

For Neon, use a deliberate pooled/direct-connection strategy. Its pooler uses transaction pooling; session-dependent features need review. Recommend a direct connection for controlled Alembic operations, verifying actual driver/pooler behavior and permissions during initialization. Do not apply arbitrary pool sizes to every process. [Neon connection-pooling documentation](https://neon.com/docs/connect/connection-pooling).

SQLAlchemy describes a Session as mutable transaction state, requiring a Session per thread or AsyncSession per task. This supports the session isolation recommendation; it does not select this project's sync/async driver. [SQLAlchemy session basics](https://docs.sqlalchemy.org/en/20/orm/session_basics.html).

FastAPI's OpenAPI output supports SDK generation. Evaluate the generator with this application's error and authentication contracts before adopting it. [FastAPI client-generation guide](https://fastapi.tiangolo.com/advanced/generate-clients/).

No recommendation changes PD-002 Stripe requirements, PD-003 R2/encrypted HLS, the seven ownership boundaries, PD-011 referral capabilities, unresolved product policies or fixed release deadlines. Additional implementation effort needs an explicit forecast update rather than a silent milestone shift.
